the problem · when done is only a claim

Prompts can delegate work.
They cannot define trusted done.

Natural-language intent, the edited repository, and the tests used to judge it can disagree. If the same worker interprets the task and grades the result, a green run may prove only the worker's chosen version of the job.

Underspecified prompts omit requirements that hidden tests enforce and that are not reasonably inferable.

Receipt
the receipt gate · two different verdicts

PRE says “may run.” POST says “may close.”

Authorization and acceptance are two independent events. One contract crosses both posts. Passing the first never implies the second, and the worker in between holds neither verdict.

PREauthorize · before work

May this run?

Size, structure, traceability, and runnable evals must all pass before the stamp. The stamp seals a TaskRevision, not a filename—edit scope, budget, or dependencies and the seal breaks.

VERDICT · DELEGATE TIER=1|2 · taskspec gate --stamp
WORKexecute · one attempt

One bounded attempt

The worker changes only the handed-off workspace and write surface. It may retry within budget, park with context, and report—it cannot accept itself.

OUTPUT · PATCH + EVIDENCE · one TaskHandoff/v3
POSTaccept · after proof

May this close?

A separate gate reruns the proof and rechecks base commit, closure, blast radius, and evidence against the same authorized attempt. Only its receipt lets status: done exist.

VERDICT · ACCEPTED=1 · taskspec accept --stamp
the rule the deck reuses The two gates answer different questions with different evidence — a green run is a candidate, not a verdict.
Story: this is the mental model the whole deck reuses. Read the five stations left to right. The leaf enters sealed as a TaskRevision. The PRE gate asks only whether it may run: effort, schema, DoD matrix, and runnable evals, then a tier-1 or tier-2 stamp. The attempt is the worker's entire authority: one workspace, one write surface, one budget. The POST gate asks a different question: may this close. It reruns the evals and rechecks base, closure, blast radius, and evidence. Only then does the receipt exist, and only the receipt lets status reach done. Point to the refusal lane: every stop is typed, and a parked attempt is not a failure hidden in chat. Transition: now see the whole loop those two gates sit inside.

Roles
the authority · who may decide

Four roles. No one issues authority to itself.

The loop works because the powers are split. An author proposes, a human authorizes, an executor works, an independent gate accepts — and every grant of authority crosses a boundary as a signed object, never as a promise inside one actor’s head.

why this matters One person can wear several hats on a small repo — but the objects still cross the boundaries, so the trail reads the same at any team size.
Story: the chat slide showed one person and one agent; this slide names the four hats that were actually in play. Walk the arrows in order. One: the author — often the agent itself — proposes a plan; proposing grants nothing. Two: the human authorizer approves the topology and stamps the seal; this is the only place a signing key exists. Three: the executor returns a patch and evidence; it worked inside the handoff and cannot widen it. Four: the acceptor answers with a receipt or a typed refusal back to the human. Then point at the red loop: the executor checking its own work and declaring done is the exact arrow prompt-based delegation relies on, and the one this system refuses. Close with the footer: on a solo repo you wear all four hats, but the objects still cross the boundaries, so the audit trail is identical. Transition: with the roles clear, open the object they pass between them — the leaf itself. Sources: OPERATING.md; src/author/; src/gate/; src/dispatch/; src/accept/.

Size
the effort gate · leaf or node

XS to L execute. XL and XXL only compose.

Size is not an estimate — it is a permission. Four tiers may be handed to an executor, each with a hard cap on how many paths it may write. Anything larger is a composition node: it holds children, owns no write surface, and can never be delegated whole.

why a hard cap A small write surface keeps the blast radius checkable — the validator enforces these caps mechanically, so “too big to review” never reaches an executor.
Story: size is a permission, not an estimate. Walk the ruler left to right. XS through M are ordinary leaves with write caps of one, two, and three paths — small enough that acceptance can compare the real diff against the declared surface. L is still a leaf but glows gold: up to five paths, one coherent done-condition, and only on a backend configured for long-horizon work (TASKSPEC_LONG_HORIZON_BACKENDS). Then the dashed frames: XL needs at least two children, XXL at least three, and nodes can nest — tasks all the way down. They own no write surface, so handing one to an executor is refused, not discouraged. Close on the italic line: the gate does not forbid ambition; it forces decomposition until every piece is individually checkable. Transition: size controls breadth; profile controls proof depth — that is the next slide.
