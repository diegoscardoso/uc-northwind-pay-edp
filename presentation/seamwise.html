the problem · how work gets sliced

Most plans cut where the calendar says.
Systems split where the seams are.

A seam is a real property of the system, not a project-management choice. Cut along it and each side changes without editing the other. Cut anywhere else and every task drags the whole estate behind it.

A seam is a place where you can alter behavior in your program without editing in that place.

Michael Feathers · 2004 ◆ Working Effectively with Legacy Code

how a seam works · the anatomy of one cut

Two sides. One joint. Change one side without touching the other.

Any system — a codebase, a pipeline, a service estate — has places where two parts hand off. Most of those joints are glued: change one part and you must edit the other. A seam is the rare joint with an explicit contract, where the side you change and the side you leave alone have different owners and independent lifecycles. SEAMWISE finds those joints with evidence, and refuses the ones that only look like seams.

check 01 · evidence
The joint exists in the system today — in code, schema, or interface — not only in the plan.
check 02 · independence
Side B can change, test and ship without one edit on side A. If it cannot, it is a false joint.
check 03 · ownership
Each side has exactly one owning lane, and the rejected alternatives are on record.
Talk track: this is generic on purpose — no data words. Point at side A and say "whatever you must not break"; side B, "whatever you are building". The blue line is only a seam if the contract box is real. Then the red dashed joints: the three classic fakes. Finish on the three checks — those are literally what the validator asks before SEAM_MAP=READY.
how swimlanes work · one seam, exactly one owner

Every seam gets one owning lane. The lane coordinates — nobody else does.

A seam is a boundary; a swimlane is who holds it. Each accepted seam is assigned to exactly one lane, and that lane owns the write surface on its side of the cut — its modules, its schema, its deploy. Every other lane may only read through the contract. Two owners on one seam, or a seam with no owner, are not planning problems to manage later: the map refuses them.

rule 01 · one seam, one lane
Every accepted seam is assigned to exactly one owning swimlane. Not a team list — one name that answers for the boundary.
rule 02 · the lane holds the write surface
Only the owning lane writes on its side of the cut. Everyone else reads through the contract — which is why legs from different lanes can run without colliding.
rule 03 · contested or orphan → refused
Two owners, or none, and map stops with exit 2 — owner input required. The gap is surfaced, never guessed.
Talk track: read the pool as a table. Left column is a name, not a department. Middle gold blocks are what that name may write. The dashed right cell is what it may only read. Then trace the two dashed crossings — the only place lanes touch is a contract. Finish on the red row: the two states the compiler will not let you carry into a plan.
how legs work · one lane, four states, one thread

A leg is a state the system can be observed in — never an activity.

Once a seam has one owning swimlane, the lane is lowered into capability legs: the ordered states the capability passes through on its way to done. Each leg names what is true and observable when it closes, not what someone did. Dependencies and shared resources decide the order — sibling legs are not automatically parallel — and the thinnest chain that proves the seam end to end is the steel thread, built first.

rule 01 · state, not activity
✗ “write the adapter”  ·  ✓ “adapter answers the contract” — a leg is named by what is true when it closes.
rule 02 · the steel thread
The thinnest chain of legs that proves the seam end to end. It is built first, so the cut is real before anything wide is built on it.
rule 03 · order by proof
Dependencies and shared resources decide the sequence. Sibling legs are not automatically parallel — the plan must justify concurrency, never assume it.
Talk track: the lane is the owner; the four cards are states, read as a sentence. Point at the gold bar first — the thread is legs 01→02, the smallest proof the seam is real. Then the red bracket: 02 and 03 touch the same routing config, so they are sequential even though they look like siblings. Finish on the three rules — those are what `plan` validates before DELIVERY_PLAN=READY.
the grammar · seam → swimlane → legs → taskplan

One seam. Four passes, each adding one guarantee.

The three previous slides, read as one compile. The seam is found and given a contract; a lane takes ownership of it; the lane is lowered into ordered capability legs; and after a human review the whole chain is projected into TaskPlan/v1 units — each one carrying its seam, lane, leg and source digest, so every unit can name its origin and nothing downstream has to guess.

Talk track: the seam core never changes — walk left to right and name what each arrow ADDS: ownership, order, lineage. The units on the right are what Task-Spec later consumes; note the red line on U-03 — even a finished projection ships with dispatch_authorized: false.

inside the taskplan · the artifact that becomes the leaves

One plan. Every unit is a leaf that can prove itself.

TaskPlan/v1 is what compile writes and what Task-Spec consumes to materialize tasks. Each unit is one future leaf: it names its goal and done-condition, the paths it may touch and must not touch, its dependencies — and carries runnable evals, so the leaf can be accepted by evidence, not by opinion. The lineage sidecar binds every unit back to its seam, lane, leg, and source digest.

seamwise/task-plan.json
{ "api_version": "taskspec.dev/v1", "kind": "TaskPlan", "approved": true, ← the review receipt made this true "metadata": { "producer": "seamwise", "seamwise_plan_status": "READY" }, "units": [{ "id": "T-01", "title": "Side B answers the contract", "effort": "S", "profile": "standard", "agent": "any", "depends_on": [], "source_note": "legs/leg-01.yaml#T-01", "touches_paths": ["side-b/adapter/**"], "creates_paths": ["side-b/adapter/contract.py"], "do_not_touch": ["side-a/**"], ← the seam, enforced per leaf "goal": "adapter answers consumes ▸ produces", "done_condition": "contract test green without one edit on side A", "rollback": "delete adapter · side A untouched", "evals": [{ "command": "make contract-test", "verifies": "the done-condition", "terminal": true }] }] }

the mechanisms · security & recovery

Six mechanisms. All of them fail closed.

None of these are conventions or discipline. Each one is enforced by the compiler — break the precondition and the pipeline stops.

1
review integrity
Digest-bound receipts

A review receipt is glued to the exact delivery-plan digest it approved. Any change to the plan makes the receipt stale — and the compile gate closes again.

stale receipt → gate closed
2
write integrity
Atomic compile

TaskPlan and lineage are written in one lock-protected transaction. Compilation is deterministic: a rerun produces identical bytes, so drift is detectable by diff.

rerun → identical bytes
3
tamper detection
Status rebuilds truth

status regenerates both expected projections from the reviewed canonical inputs. Altered, partial, extra, or stale boundary artifacts fail — even if both files were edited together.

tampering → fail closed
4
filesystem safety
Canonical paths

Repository paths are canonicalized and checked against traversal, case tricks, glob abuse, collisions, and symlink escape before anything is read or written.

escape attempt → refused
5
authority hygiene
No credential reach

SEAMWISE never receives Task-Spec credentials or signing keys. The capabilities contract advertises materializes_tasks: false and dispatch_authority: false.

no keys · no dispatch
6
reporting hygiene
Reports create no authority

HTML reports and chat packets explain verified state — they cannot review a plan, materialize a task, or mint Task-Spec authority. Reading is never a side effect.

explain · never authorize
Talk track: pick two — the digest binding (card 1) and the rebuild check (card 3) — and explain that together they make the review boundary unfakeable: you cannot re-point a receipt, and you cannot hand-edit the outputs. The other four are the supporting cast.
the cli · one binary, one result contract

Every command returns exactly one object

The whole surface is one binary. In --json mode every command emits a single SeamwiseCLIResult/v1 — an exact token, the artifact paths, diagnostics, and the next safe action — so an agent never has to parse prose. The exit code is the gate speaking: 0 means the intended boundary was reached, 2 means a human input is required. The one highlighted line is the only command a machine cannot run for you.

seamwise --help
# author & compile seamwise init # workspace seamwise recipe schema # the authoring contract seamwise map --source recipe.yaml seamwise plan # stops at NEEDS_REVIEW seamwise review --accept --reviewer <name> --reason <why> seamwise compile # two artifacts, atomic seamwise prepare --source recipe.yaml # automates, still stops at the gate # inspect & report seamwise status · next · inspect [TASK_ID] · graph seamwise report --format html|json seamwise capabilities # the machine boundary # hosts & health seamwise agent-context --host codex|claude|chat seamwise install codex|claude|all --scope project|user seamwise doctor --host core|codex|claude|all

the skills · agents drive the same cli

Five skills. The chat proposes — it never decides.

Installed into Codex, Claude Code, or both. Every skill drives the shared CLI; none recreates compiler behavior in the model. A chat may propose each pass and run its gates, but review, materialization, and dispatch remain outside the conversation.

The skill sheet skills/ · one per boundary
  • $seamwise the orchestrator — one confirmed pass at a time, one question at a time status → next safe action
  • to-seam-map discover and challenge seams — evidence, owners, rejected alternatives SEAM_MAP=READY
  • to-delivery-plan form swimlanes, legs, steel thread — objections stay OPEN until an owner rules DELIVERY_PLAN=READY
  • to-task-graph compile the dependency-safe graph — cycles, collisions, critical path TASK_GRAPH=READY
  • to-task-specs project the reviewed plan into TaskPlan/v1 + lineage — then stop dispatch_authorized: false
